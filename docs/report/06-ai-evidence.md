# 6. AI 证据日志

本章说明小组如何把大语言模型（LLM）的回答当作**待验证假设**使用：怎么提问、怎么核验、哪些回答被纠正。逐条原始记录在 [AI 日志](../evidence/ai-log.md)（共 18 条）和各 Issue 的 `issue-<编号>.md`；本章只做归纳与案例分析。

## 6.1 提问与核验方法

1. **提问**：多数提问是围绕具体源码行为的封闭问题，如“`RolloutBuffer.reset()` 会不会把数组清零？”“`predict` 里 `deterministic=False` 怎么采样？”。少数是任务级请求（如“帮我完成这个 issue”）。
2. **记录**：每条记录写模型、提问摘要、AI 结论、验证方法、结果和修正后的表述；AI 结论不直接进入结论表。
3. **核验手段**，按强度排序：运行代码并断言（脚本、实验）> 对照固定 commit 的源码与行号 > 上游测试 > Issue/PR 历史。纯文字推理不算核验。
4. **复核**：由非提交者对照固定基线复查，AI 记录也在复核范围内。T04 的复核说明里明确写到，作者最初把 AI-04-02 记成“已核验基本正确”，复核时才发现是错的（见 6.3）。

使用的模型按记录：GPT-4o-mini（T03、T04）、WorkBuddy 会话中的 LLM（T05、T08）、Codex（T06）；T01 的原始记录未注明模型。

## 6.3 案例一：AI 说“不重新分配数组”，运行证伪（AI-04-02）

**提问**（T04，GPT-4o-mini）：`RolloutBuffer.reset()` 会把 observations/actions 清成 zeros 吗，还是只移动指针？

**AI 回答**：为了性能不会重新分配大数组，只重置 `pos=0`，下一次 `add` 覆盖。

**假设形成**：这个说法在工程上很合理——很多环形缓冲区确实这样做，所以最初被记为“已核验基本正确”。

**核验**：复核人读 [buffers.py:L391-L401](https://github.com/DLR-RM/stable-baselines3/blob/7cfb4dd6055e74b5caa4ed4d6777492209946e26/stable_baselines3/common/buffers.py#L391) 发现 `reset` 重新创建了归零数组，然后改写脚本：保留旧的 `observations` 引用，把它填成 9，再调用 `reset()`，断言 `buffer.observations` 已是**新对象且全零**（脚本 [issue_04_learn_trace.py](../../scripts/issue_04_learn_trace.py) 的 E 节，输出 [output.log](../../artifacts/runs/issue-04/2026-10-15-review/output.log) 中 “✓ reset 重新分配并归零 observations”）。

**结论**：AI 的回答被源码和运行同时否定；而“已核验”的原始记录也是错的，因为作者只做了推理，没有让旧引用暴露出差别。附带发现另一个误解：`generator_ready` 控制的是展平，而不是随机置换；`get()` 每次调用都会重新 `np.random.permutation`（C-04-05）。

**教训**：“看起来合理”的性能优化说法最容易被默认接受。能用一个小断言区分的行为，就不要停留在读代码——这里的区分方法是保留旧引用再检查。

## 6.4 案例二：AI 的假设成立，但只在特定条件下（AI-05-02、AI-05-01）

**提问**（T05）：`Sequence`/`Graph`/`OneOf` 观测空间下 `check_env` 的行为？

**AI 假设**：会警告并跳过后续返回值检查，可能静默通过。

**核验**：对照源码 `env_checker.py` L147-L169、L531-L535，并设计实验 W09：环境返回非法字符串观测 `"not-an-observation"`，`check_env(..., warn=True)` 仍然通过，只给出一条警告；实验 F12 把 `warn` 改为 `False`，同一非法观测则触发 `AssertionError`（[运行记录](../../artifacts/runs/issue-05/2026-10-12-env-checker-review-fixes/summary.md)）。

**结论**：AI 的假设被运行证实，但它没有说明条件——跳过检查**只在 `warn=True` 时发生**。结论因此被限定为“`check_env` 通过不能视为环境正确的充分条件”，状态为“需限定”（C-05-07）。同一任务里 AI-05-01 也漏掉了类似的条件：无限动作边界的断言仅在 `warn=True` 分支内（C-05-08）。

**教训**：这类 AI 错误不是“说反了”，而是**省略前提**。运行实验要同时设置对照（`warn=True` 与 `False`），才能把前提找出来。

## 6.5 案例三：把标签动作读成关闭决定（AI-08-01、AI-08-04）

T08 要找“Issue → PR → commit”完整链条。AI 先推荐 Issue #1950 当主案例，核验发现它没有任何 PR/commit，假设被否定，改为 #2172 → PR #2174，#1950 降为对照（AI-08-01）。之后复核人又指出 AI 的两处表述不准确：把 PR 里的“递归”一词沿用到实现描述上，实际只遍历 `Dict`/`Tuple` 的直接子空间；把维护者改标签概括成“判定不改并关闭”，而 `closed_by` 其实是报告者本人（AI-08-04）。小组把这两条修正固化为可重跑的检查（见 [issue-08.md](../evidence/issues/issue-08.md) 中的 V-08-14 至 V-08-16）。

这一案例的特点是错误来自**对文字材料的转述**，不是对代码的理解；核验手段是调用 GitHub API 取原始事件，而不是再问一次 AI。

## 6.6 错误类型归纳

| 类型 | 例子 | 有效的核验方式 |
|---|---|---|
| 类关系或归属说反 | AI-04-01（把 `PPO.learn` 当成主循环所在）、AI-01-03（DDPG 继承 TD3） | 搜索全部 `class X(` 定义；读 `super().learn` 的转发 |
| 把常见做法当事实 | AI-04-02（不重新分配）、AI-03-01（`predict` 直接走 `forward`） | 保留旧引用、profile 调用路径，断言实际路径 |
| 省略前提或分支 | AI-05-01、AI-05-02、AI-03-02、AI-04-03 | 对同一场景改变开关做对照实验 |
| 把 AI 的解释当算法性质 | AI-04-03（把 clip 说成防止偏离的保证） | 只验证软件控制流，不推断数学性质 |
| 转述材料失真 | AI-08-02、AI-08-04 | 取原始 API 数据与 diff，逐条比对 |
| 行号或版本细节错 | AI-01-04、AI-08-03 | 在固定 commit 上按行号核对 |
