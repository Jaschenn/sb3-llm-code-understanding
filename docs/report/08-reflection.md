# 8. 学习反思

本章的材料只来自仓库里的 `docs/evidence/issues/issue-<编号>.md`：各任务的“复核记录”、AI 使用记录，以及这些记录引用的运行目录。不使用 GitHub 页面上的 review 和提交署名，也不按个人提交量评价贡献。因此这里写的是**记录里反复出现的问题和由此形成的做法**，不是对某个人想法的转述；没有写在记录里的体会，不在本章代写。

## 8.1 取材与归类方法

- **取材**：issue-01、03、04、05、06、08 的复核记录（含 T03、T04 的“第二轮审慎检查”“第三轮复核”）。issue-02、issue-07 是本报告补写时新增的，不作为复核样本。
- **归类**：把每条“复核指出的问题”或“复核后的修正”归入下表的类型。归类由本章作者完成，一条记录可能同时属于几类；表中“出现于”只列任务，不统计条数。
- **限定**：issue-05 的复核记录只有两条修正，issue-06 的复核主要是验证结果与审批例外说明，所以这两个任务贡献的样本较少。

## 8.3 这些问题怎样变成做法

复核记录里能看到一条清晰的演变：先改错，再把“怎么发现这个错”固化下来。

1. **从改文字到加检查。** T08 复核指出三处表述不准确后，没有只改文字，而是新增 V-08-14、V-08-15、V-08-16 三项机械校验，重跑后 16 项全部通过。下次有人改这些结论的措辞，脚本还能再报警。
2. **检查自身也要被检查。** T04 增加反向验证 `check_disabled_training.py`：模拟只增加更新计数、完全不修改参数的 `train`，要求参数断言拒绝这种情形。这是在证明“这个检查确实能发现问题”。
3. **通过的测试数不等于执行的断言数。** T03 第三轮说明，54 个通过的用例里有 3 个上游参数组合直接返回，不计作实际执行了预测断言。
4. **历史记录保留，不被覆盖。** T03、T04、T05 都写明原运行目录保留、新输出放到新目录；T06 复核时不修改原始运行记录，只追加复核说明和输出。这使得“前后不一致”本身成为可见的证据（T06 的 161.3 与 485.6）。

## 8.4 AI 辅助：有效帮助、错误类型与核验成本

细节见[第 6 章](06-ai-evidence.md)，这里只写和 8.2 的对照。

- **有效帮助**：AI 提出的具体假设可以变成实验。T05 的 W09 实验就是把“会警告并跳过返回值检查”这个假设写成可复现的运行（C-05-07）；T06 里 AI 建议的最小预测、环境检查和短训练也被采用并保留原始输出。T08 里 AI 先推荐 #1950，核验后被否定，反而促成了“主案例 + 对照案例”的结构。
- **错误类型与 8.2 重合**：AI 的错误集中在“把常见做法当事实”“省略前提”“转述失真”，与复核记录里的“与源码不符”“过度推论”“遗漏前提”是同一批问题。也就是说，**人写的材料和 AI 给的材料犯的是同一类错**，核验手段也相同。
- **核验成本**：记录显示 T03、T04 各有 3 轮复核记录，另有 4 个运行目录；T06 有 5 个运行目录。核验通常需要多轮，并且常要补写脚本，而不是读一遍代码就结束。
- **来源的差别**：AI-04-02 的原记录是“已核验基本正确”，说明**核验也会被推理代替**。能区分两种可能的断言（保留旧引用再检查）比再读一遍代码可靠。

## 8.6 对后续工作的建议

1. 写结论时同时写“成立前提”；复核时先查前提，再查结论。
2. 对“默认值/性能/内部路径”类说法，先写一个能区分两种可能的断言，再看结果。
3. 凡要引用运行结果，脚本必须证明被测代码就是固定基线（T03、T04、T05 已各自实现，可抽成公共函数）。
4. 单次运行的数字（如 CartPole 均值）一律标“需限定”，除非能稳定复现。
5. 复核和审批分开记录：复核意见写入 issue 文件，同时请一位非提交者在 PR 上批准。
6. 从第一天记录 AI 提问和模型名；T01 的原始记录就缺模型名。
